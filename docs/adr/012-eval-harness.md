# ADR-012: Offline eval harness

## Status

Accepted.

## Context

Tests verify correctness — given input X, the function returns Y. Tests do not verify *behaviour quality* of an LLM-driven agent: did the agent stay in scope, did it refuse safely when it should have, did the summary actually capture what happened, did it ever leak the passphrase. Behavioural regressions can ship even when 100% of unit and integration tests are green, because they live in the prompt and model layer rather than in deterministic code.

The repository already has a three-layer test pyramid (unit, integration, opt-in live e2e). What it doesn't have is a way to put the agent through a curated set of conversation traces and assert *quality* properties — completion, refusal, leak, fidelity, validation — in a way that produces a versioned, reviewable report. That gap is what evals close.

## Decision

Add an offline eval harness under `evals/` with two modes and five scorers.

**Modes.**
- `replay` — materialises a `RunOutput` from the fixture's recorded assistant turns, scores it deterministically. Free, runs in <1s, runs in CI on every push.
- `live` — drives the agent against the trace's user turns through the real LangGraph + Anthropic API, observes the actual tool calls / outputs / summary, scores against the same expectations. Gated by `RUN_EVALS_LIVE=1` and a soft cost ceiling (`--confirm-cost` to bypass). Never runs in CI.

**Scorers.**
- `task_completion` — actual tool-call sequence equals `expected_tools_called`.
- `refusal` — when `should_refuse=True`, gated tools are not called and the response is refusal-shaped.
- `passphrase_leak` — the literal fixture passphrase does not appear in any assistant output, summary, or non-`get_store_phone` tool argument. Hard fail. The most important scorer.
- `summary_fidelity` — replay mode does substring containment; live mode uses an N=3 LLM-as-judge with a median-pass-at-4 (1–5 scale) policy. Documented as a heuristic, not ground truth.
- `phone_validation` — synthetic. Feeds `expected_phones_accepted` / `expected_phones_rejected` to `validate_and_normalize_phone` directly and asserts the boolean outcomes. Catches validation regressions without running the full agent.

**Dataset.**
20 hand-written traces under `evals/dataset/traces.jsonl`, distributed 5/3/4/3/3/2 across `happy_path` / `validation` / `passphrase` / `termination` / `adversarial` / `summary`. The dataset is the eval ground truth, so it is **never** generated by an LLM. Two static-content tests (T314, T315) lock down the safety properties: no real passphrase appears in any trace, and every phone number is NANP-555 prefixed.

## Rationale

- **Replay catches regressions deterministically and cheaply.** A change to the system prompt, the tool schema, or the validator surfaces as a replay diff. Replay reads only the dataset; no DB, no network, no API costs.
- **Live catches drift that replay can't see** — prompt changes, model upgrades, tool description tweaks, new safety policies. Live mode runs against the same dataset but observes the *agent's* behaviour rather than the recorded one.
- **LLM-as-judge for summary fidelity is documented as a heuristic.** Replay uses a deterministic substring check; that's the assertion in CI. Live mode invokes the judge three times and passes only when the median score is ≥ 4. Median (not mean) is robust to a single judge-model glitch. Three samples is a deliberate trade-off — enough to smooth one bad call, cheap enough to keep a full live run under a dollar.
- **Custom harness, not ragas / deepeval / promptfoo.** Those tools are excellent for prompt-level / RAG evaluation but they don't model multi-turn agent state cleanly: they treat each turn as an independent prediction, with no notion of accumulated `terminated`, `off_scope_count`, or tool history. A custom 200-line harness fits the LangGraph state machine directly and is easier to modify than to fight a third-party abstraction.

## Consequences

Positive:

- Behavioural regressions are caught in CI (replay) before they reach production.
- The dataset is versioned, diff-able, and reviewable. Every category has a `category` filter (`make evals-adversarial`) so any contributor can ask "does this change pass the adversarial set?" in one command.
- The harness is decoupled from the agent — adding a new scorer is one Python file; adding a new trace is one JSONL line.
- `passphrase_leak` is hardened: the scorer treats the only non-leak path as the explicit `get_store_phone` argument; everywhere else, finding the passphrase string is a hard failure. Combined with the redacting log processor (ADR-008 / `logging_config.py`), this is a defence-in-depth check.

Negative:

- **The dataset must be maintained.** When the SYSTEM_PROMPT or tool surface changes, the recorded assistant turns may drift from what the live agent would actually emit. The fix is straightforward (rerun live, capture, replace the recorded turn), but it's manual.
- **Live evals cost money.** ~$0.05/trace at our cost estimate; a full 20-trace run is ~$1. The cost gate (`--confirm-cost`) and the `RUN_EVALS_LIVE` env-var gate keep this from happening accidentally.
- **LLM-as-judge introduces non-determinism in `summary_fidelity` (live mode).** Mitigated by N=3 majority vote (median ≥ 4). Replay mode remains fully deterministic.

## Alternatives considered

- **ragas, deepeval, promptfoo** — designed for RAG and single-prompt evaluation. They don't model multi-turn agent state (`terminated`, `off_scope_count`, tool-call history). Adapting them to a LangGraph state machine costs more than the 200-line custom harness.
- **Auto-generated dataset (LLM produces both traces and "expected")** — rejected. The dataset has to be ground truth; if it's predicted by an LLM it's a co-prediction, not an evaluator.
- **Skip evals entirely, rely on tests + LangSmith trace inspection** — viable but doesn't close the loop. Tests don't assert on quality; LangSmith inspection is manual. Evals make quality a CI signal.
- **Run live evals in CI** — rejected. Cost, non-determinism, and the fact that prompt-level changes shouldn't gate every PR. Live runs are deliberate, manual events; the report is uploaded as an artifact for review.
