# Production Readiness

This document describes how the current scaffold would be hardened for production. The current implementation prioritises clarity for review; the items below are explicit gaps and the plan to close them.

## Scalability

The backend is designed to be stateless: per-turn agent state is reconstructed from persisted conversation history rather than held in memory. That property lets us scale horizontally behind a load balancer without sticky sessions. PostgreSQL is the only stateful tier. Connection pooling is sized via SQLAlchemy's `pool_size` and `max_overflow` based on `(replicas × concurrency_per_replica)`, with a hard cap below the Postgres `max_connections` budget; a PgBouncer (transaction pooling) sits in front of RDS to absorb burstiness. Read replicas serve read-heavy retrieval traffic; writes go to the primary. Shared session state (in-flight conversations, idempotency keys) lives in Redis when we need cross-replica coherence beyond what the database provides. Capacity planning starts from p99 LLM latency and target conversations-per-second; replicas are autoscaled on CPU and on a custom metric (in-flight LLM calls per pod) to avoid thrash.

## Resilience

LLM calls are wrapped with `tenacity` for exponential backoff with jitter on 5xx and rate-limit responses, capped at a small retry count to bound tail latency. Per-call timeouts come from `asyncio.timeout`; per-conversation budget is enforced so a stuck graph cannot pin a worker. A circuit breaker opens after consecutive provider failures and sheds load to a degraded path that returns a clear "service temporarily unavailable" message rather than failing silently. Database calls retry on transient errors (deadlocks, connection drops) and surface non-retryable errors immediately. Validation errors emitted by tools are returned to the LLM as structured `ToolMessage` content so the model can self-correct rather than the call hard-failing. Health checks are split into liveness (process up) and readiness (DB reachable, model reachable) so an LLM outage drains traffic but does not cycle pods.

## Security

Secrets move from `.env` files to AWS Secrets Manager (or Vault) and are mounted into the container at runtime via IRSA / IAM roles, never as plaintext env in the deployment manifest. The Postgres tier sits in private subnets; only the backend security group can reach it, and TLS is enforced end-to-end. Inputs are validated at every system boundary (UI → agent, LLM → tool, tool → repository) using the Pydantic schemas described in ADR-005. Outputs are filtered through a PII scrubber before persistence and before tracing; an output classifier inspects free-text responses for compliance violations (see Compliance below). Logs are redacted at the structlog processor level so secrets and PII never reach the log sink. Dependency hygiene is enforced via `pip-audit` and `bandit` in CI; image scanning runs on every container build.

## Failover

PostgreSQL runs as Multi-AZ RDS with automated backups, point-in-time recovery, and a tested failover runbook. SQLAlchemy reconnects automatically on dropped connections; the application surfaces a transient error and retries once for idempotent operations. All database operations on a single store record are designed to be idempotent (upsert on natural key, soft-delete with timestamps) so a retry after a partial failure converges to the same state. The LLM layer has a fallback chain: primary Sonnet on Bedrock → fallback Haiku on Bedrock → static degraded response. Cross-region disaster recovery uses RDS read replicas promoted on demand; the application reads its DB endpoint from a service-discovery DNS name so failover does not require a redeploy.

## Caching

A Redis layer caches three things: per-conversation working state (so a turn can be served by any replica), idempotency tokens for tool calls, and a semantic cache for repeated retrieval queries by phone (TTL-bounded). Anthropic prompt caching is enabled for the system prompt and tool definitions, which yields 50–90% cost reduction on the cached portion at typical reuse patterns and reduces input tokens billed per turn substantially. Deterministic lookups (e.g., reference data) are cached in-process with a short TTL. Cache invalidation rules are explicit: writes to a store record purge the relevant Redis keys atomically with the DB write via outbox-style messaging or cache-aside with versioned keys. Cache hits are logged and metered so we can detect a degraded cache without it silently inflating latency.

## Token cost optimization

Cost is driven by input tokens (system prompt + history) more than by output tokens, so the largest lever is Anthropic prompt caching applied to the system prompt and the tool schemas. Model routing splits the workload: a cheap Haiku call classifies intent and decides whether the conversation is on the save, retrieve, or terminate path, and Sonnet only handles the actual tool-calling step. Conversation history is summarised after a configurable threshold so the context window does not grow unbounded across long sessions. Streaming output is enabled to reduce perceived latency; users do not wait for the full response before seeing tokens. Asynchronous batch jobs (e.g., overnight re-summarisation) run via Anthropic's batch API at lower cost. Token usage per request is metered and exported as a Prometheus metric so we can detect regressions in prompt size before the next invoice.

## Observability

Logs are JSON-structured via structlog and shipped to CloudWatch (or ELK), with one schema across the stack: `request_id`, `conversation_id`, `node`, `tool`, `latency_ms`, `tokens_in`, `tokens_out`, `outcome`. Metrics are exported in Prometheus format and ingested by Datadog: request rate; latency p50 / p95 / p99 per node and per tool; tool-call success rate; LLM tokens (input, output, cached) per minute; DB query latency per repository method; error rate by class. Distributed tracing uses OpenTelemetry spans across the agent → tool → repository → DB chain, with W3C trace context propagated to LLM calls where supported. Alerts fire on SLO breaches (e.g., p95 latency > target for 5 minutes, error rate > 1%, LLM provider error rate > 5%) and page on-call via the standard pager rotation. Dashboards are owned, named, and linked from the runbook.

## Compliance for the regulated FS deployment

Consumer-facing financial-services agents operate under CFPB UDAAP oversight, state PII regimes (CCPA and peers), and, where applicable, NYDFS Part 500. Every agent output passes through a compliance classifier before display: it flags misrepresentations, missing required disclosures, and language that could be construed as legal or tax advice. Flagged outputs are blocked or rewritten to a compliant template, with the original captured for review. Audit logging is non-negotiable: every tool call is persisted with full inputs and outputs, the model name and version, the prompt template version, and a tamper-evident checksum, retained per applicable retention windows. PII is encrypted at rest (RDS KMS) and redacted in conversation summaries before persistence so analytics queries do not expose customer identifiers. Access to the audit log is least-privilege and reviewed quarterly.

## Deployment

The backend ships as a container image to ECR and runs on ECS Fargate (or EKS, depending on platform standard). Deployments are blue/green: a new task set is brought up, health checks pass, traffic shifts in steps (10% → 50% → 100%) with automatic rollback on error-rate or latency regression. Database migrations run as a one-shot ECS task (`alembic upgrade head`) gated to complete successfully before the new application version receives traffic; the migration job and the application deployment are linked in the pipeline so a failed migration aborts the rollout. Secrets are wired in via IAM-backed Secrets Manager references, not baked into the image. Image provenance is tracked (SBOM generated at build, signed with cosign, verified at deploy). Rollback is one command and is exercised in game days.
